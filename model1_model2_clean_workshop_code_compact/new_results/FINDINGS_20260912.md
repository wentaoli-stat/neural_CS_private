## Read this first: which comparisons are fair

The readout is trained by a different flag in each codebase, and this session tuned the flags unevenly:

- **p=1** (`model1/stage1.py`): linear trains with `--lr`; gate/stacked train the readout with `--joint-rho-lr` and the local branch with `--gate-lr`.
- **p=3** (`model1_p3/stage1.py`): linear and the gate/stacked readout all train with `--lr`; the branch with `--branch-lr`. The `lr 1e-3` linear runs were separate invocations from the gate/stacked runs, which used `--lr 1e-4`.

**Consequence.** Raising linear to `1e-3` raised only linear's readout. Every comparison of a nonlinear map against `linear, lr 1e-3` below is flagged **UNMATCHED**: linear's readout trains 10× faster than the nonlinear readouts it is compared with. Those gaps are not a fair nonlinear-versus-linear estimate and could be biased in either direction, because the nonlinear branches *did* train at `1e-3`. Clean, readout-matched comparisons are: **stacked vs gate**, the **linear learning-rate audit** (same method, only the rate changed), and the **p=1 bandwidth comparison**. A fair nonlinear-versus-linear estimate needs gate and stacked rerun with their readout at `1e-3` too.

## 4. Input representation: structure beats information

Three reference inputs with no ILSA nesting, so no warm start. Each has *more* information than pooled linear.

Each input at its better learning rate, 40k budget: raw `0.806` > all subscores `0.592` > per-block unpooled `0.307` > pooled linear `0.236`. The per-block stack keeps block additivity and sees every subscore, yet with both at `lr 1e-3` it is **worse than simply averaging them** (paired +0.07181, SE 0.00595; linear better on 5/5), so within-group pooling is actively helpful at this budget, not merely harmless.

*This depends on the learning rate.* With both at `lr 1e-4` the ordering flips (paired -0.01366; per-block better on 4/5), but only because `lr 1e-4` under-trains linear (§1): the per-block stack barely moves between the two rates (`0.311` at 1e-4, `0.307` at 1e-3) while linear improves by about a quarter. Raw and all-subscores overfit within the first few thousand steps (they select steps 500–2,500 of 20,000).

*Checkpoint-grid check.* Validation ran every 500 steps for these baselines vs 200 for the others. Rerunning raw and subscores with a 50-step grid changed nothing: raw +0.00235 (SE 0.00141), subscores +0.00184 (SE 0.00155).

## 7. Tube bandwidth: the draft's rule (seed 20260709)

`main_style_revised` initializes `Σ_q = 2Σ_e`, Σ_e the pilot-error covariance. With an efficient pilot Σ_e ≈ E[I⁻¹] over the anchor prior, giving σ_q = 1.052 at p=1 (vs packaged 0.20, 5.3×) and (0.821, 0.162, 0.050) at p=3.

**p=1**

| arm | narrow σ_q | draft σ_q | change | readouts |
|---|---:|---:|---:|---|
| linear | 0.03408 | 0.50788 | +1390% | matched |
| gate | 0.02335 | 0.50151 | +2048% | matched |
| stacked m_dim=8 | 0.02039 | 0.49927 | +2349% | matched |

**p=3**

| arm | narrow σ_q | draft σ_q | change | readouts |
|---|---:|---:|---:|---|
| linear | 0.22815 | 0.53257 | +133% | matched |
| gate | 0.21050 | 0.52259 | +148% | **UNMATCHED** (0.0001 vs 0.001) |
| stacked m_dim=8 | 0.19631 | 0.52312 | +166% | **UNMATCHED** (0.0001 vs 0.001) |

Every method collapses to nearly the same error at the draft bandwidth — the signature of a shared smoothing-bias floor. **This does not show the draft's rule is wrong**: the rule deliberately accepts smoothing bias so the field is accurate where a pilot lands, while this metric measures error at the true β, where the narrow tube is favoured by construction. Bandwidth cannot be chosen from Stage-1 exact-score MSE; it needs Stage 2. At p=3 only the linear row is readout-matched, but it alone shows the collapse. The packaged σ_q = 0.20 does not follow the draft's stated initialization; it may be the tuned value, which the draft does not document.
